# UnSOLO iOS app

**Status:** P2 native app, simulator build (Nov 2026). It builds, runs and passes its unit tests on the iOS Simulator with signing disabled. Nothing has run against a deployed backend yet: every screen is exercised through demo mode, which serves the [API v1 contract](api-v1.md) from bundled fixtures. TestFlight needs the inputs listed in [Inputs needed from the team](#inputs-needed-from-the-team).

**Code:** `mobile/ios/`. The app is SwiftUI on Swift 6 with strict concurrency and targets iOS 17.0+ on iPhone. It has no third-party dependencies, so it builds offline.

## Build and run

You need Xcode 26 or later and an "iPhone 17" simulator (`xcrun simctl list devices available`).

```sh
# Build (Debug, demo mode on)
xcodebuild -project mobile/ios/UnSOLO.xcodeproj -scheme UnSOLO -sdk iphonesimulator \
  -destination 'platform=iOS Simulator,name=iPhone 17' CODE_SIGNING_ALLOWED=NO build

# Unit tests (68 tests)
xcodebuild test -project mobile/ios/UnSOLO.xcodeproj -scheme UnSOLO -sdk iphonesimulator \
  -destination 'platform=iOS Simulator,name=iPhone 17' CODE_SIGNING_ALLOWED=NO

# Install, launch and screenshot every main screen (boots and then shuts down the simulator)
mobile/ios/tools/screenshots.sh                       # → mobile/ios/screenshots/*.png
mobile/ios/tools/screenshots.sh /tmp/shots tribe chat # chosen screens, other folder
```

**In Xcode:**
1. Open `mobile/ios/UnSOLO.xcodeproj`.
2. Pick the shared `UnSOLO` scheme and an iPhone simulator, then press Run.
3. Simulator builds are unsigned (`CODE_SIGNING_ALLOWED[sdk=iphonesimulator*] = NO` in `Config/Base.xcconfig`), so no team is needed.

**Project format:** the project is hand-written with `PBXFileSystemSynchronizedRootGroup` (objectVersion 77).
- Any file you add under `UnSOLO/` or `UnSOLOTests/` is picked up automatically. There are no per-file entries in `project.pbxproj`.
- `Info.plist` and `UnSOLO.entitlements` are excluded from the synchronized group through a membership exception.

## Demo mode

The backend isn't deployed yet, so Debug builds use `DemoTransport` (`Networking/DemoTransport.swift`) by default. It is an in-process fake of every `/api/v1` route the app calls, plus Supabase Auth (`/auth/v1/token`, `/signup`, `/otp`, `/verify`, `/logout`, `/recover`).

**Fixtures:**
- Files: `UnSOLO/Resources/Demo/*.json`, generated by `python3 mobile/ios/tools/make_demo_fixtures.py`. Edit the script, not the JSON.
- Content: realistic Indian trips (Chalo Himachal, Spiti Winter Circuit, Kheerganga, Valley of Flowers, Rishikesh, Tungnath, Bhutan, Rupin Pass, plus stays, activities and rentals), Tribe plans, stories and asks, comments, host offers, join requests, bookings, notifications, chats and profiles.
- People: Ananya, Rohan, Kabir, Riya, Meher and others. The host is Tent It India.
- Viewer: the demo user is "Dev Sharma". He is phone and ID verified, and also a host, so every screen is reachable.
- Images: `demo://` URLs, rendered locally by `DemoImageRenderer` as generated landscapes, avatars and the logo. No photos are downloaded.

**Behaviour:**
- It follows the contract's rules:
  - idempotent `clientId` (a replay returns 200 with the original object)
  - `phone_required`
  - join intro of 10–500 characters, with the seat marked `requested`
  - organiser approve/decline
  - accept/decline on host offers
  - moderation: money words hold the post, phone, UPI and email are hidden, outside links are flagged
  - chat `?after=` polling, where direct chats get a scripted reply about 5 s later so you can watch polling work
  - `/sync`
- Mutations are saved to `Application Support/demo-state.json`, so what you post survives relaunches. `-resetState YES` clears them.
- Credentials: any email with a 6+ character password works, and every OTP is `123456`. Signing in with an email other than `dev@example.com` starts with an unverified phone, so you can try the phone-verification gate.
- Fallback: if a non-demo build can't reach the server on its **first** launch (no cached config), it switches to demo data and shows "Server unreachable · showing demo data".

## Architecture

```
SwiftUI views ──read──▶ @Observable repositories ──read/write──▶ LocalStore (SwiftData cache)
      │                         │  ▲                                     ▲
      │ actions (optimistic)    │  │ refresh (stale-while-revalidate)    │ handlers replace optimistic rows
      ▼                         ▼  │                                     │
   Router / gates         APIClient ──▶ HTTPTransport ──▶ URLSession (URLCache) | DemoTransport
                                ▲             ▲
                          AuthManager    OutboxEngine (pending writes, clientId, backoff)
                   (Supabase REST, Keychain,       ▲
                    single-flight refresh)    UploadCoordinator → BackgroundUploader (background URLSession)
```

**Composition root:** `App/AppModel.swift` owns the transport, `AuthManager`, `APIClient`, `LocalStore`, `OutboxEngine`, `Analytics`, `LandingTracker` and `UploadCoordinator`, plus the repositories (`SessionStore`, `ExploreRepo`, `TribeRepo`, `TripsRepo`, `ActivityRepo`, `ChatRepo`, `ProfileRepo`). All of them are `@MainActor @Observable`.

**Navigation:** `App/Router.swift`.
- Each tab (Explore, Tribe, My trips, You) keeps its own `NavigationStack` alive.
- Pushed screens are typed `Route` values.
- `(+) Post` opens the post-type sheet instead of switching tab.
- The tab bar is drawn by hand to match Passenger Chart: a flat paper bar with an ink rule and an ink "Post" pill. It hides on pushed screens.
- Messages and Activity icons sit in every root header.

**Models:** `Models/APIModels.swift` mirrors the "Shared models" section of api-v1.md (camelCase, paise, `YYYY-MM-DD` dates, ISO-8601 timestamps with or without fractional seconds). Arrays the server may omit decode as `[]` through `@DefaultEmpty`. `FeedItem` decodes the feed's mix of posts and `placed_trip` cards.

### Networking

- **`APIClient`** (`Networking/APIClient.swift`):
  - Adds `Authorization: Bearer` and `X-UnSOLO-Client: ios/<version> (<build>)`.
  - Maps the error envelope to `APIError`, including `phone_required`, `rate_limited` + `Retry-After`, and `upgrade_required`.
  - On a 401 it refreshes once and retries.
- **`AuthManager`** (an actor) talks to Supabase Auth REST directly with `apikey`.
  - Supported flows: Google (OAuth + PKCE, below), email + password, email code, phone code, refresh, logout and recover.
  - Refresh is **single-flight**: concurrent 401s share one refresh, which a test covers.
- **Token storage:**
  - The session lives only in the **Keychain** with `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly`.
  - I verified that the Keychain works on the unsigned simulator build: the session survived a relaunch.
  - If the Keychain is ever unavailable, the token is held in memory for that launch only. It is never written to disk in plain text.
- **`URLSessionTransport`:**
  - `URLCache` with 20 MB of memory and 100 MB of disk. It honours `Cache-Control` and `ETag`, so stale public GETs are revalidated with `If-None-Match` and a 304 is served from cache.
  - Private GETs are `no-store` on the server side.
  - The cache is wiped on sign-out.
- **Config:** `GET /config` loads at launch and every 15 minutes. It provides the kill-switch flags (`tribePostingEnabled` disables posting, `hostOffersEnabled`, `pushEnabled`), the Supabase URL and key, and `minAppVersion.ios`, which triggers an update alert.

### Google sign-in (no SDK)

"Continue with Google" is the first option on the welcome sheet (`Networking/OAuth.swift`, `SessionStore.signInWithGoogle`):
1. Generate a PKCE verifier (32 random bytes, base64url) and its S256 challenge.
2. Open `{supabase.url}/auth/v1/authorize?provider=google&redirect_to=unsolo://auth-callback&code_challenge=<S256>&code_challenge_method=s256` in `ASWebAuthenticationSession` (callback scheme `unsolo`).
3. Parse `code` from `unsolo://auth-callback?code=…`. Only that exact scheme + host is accepted; `error_description` is shown, and cancelling is silent.
4. Exchange the code via `POST {supabase.url}/auth/v1/token?grant_type=pkce` with `{ auth_code, code_verifier }`. Tokens go to the Keychain like every other sign-in.

In demo mode the exchange is answered locally and signs in the demo traveller. **Team action:** add `unsolo://auth-callback` to Supabase → Authentication → URL configuration → Redirect URLs. It reuses the Google provider the website already has, so no new Google client is needed. Sign in with Apple stays shown but disabled.

### Offline-first cache and sync

- **SwiftData models** (`Persistence/CacheModels.swift`): `CachedPost`, `CachedTrip`, `CacheEntry` (feed and explore orderings, trip details, my trips, `/me`, preferences, suggestions, profiles), `CachedComment`, `CachedNotification`, `CachedChat`, `CachedMessage` and `OutboxItem`.
  - Each row stores the contract JSON plus the columns needed to query and sort it.
  - Feeds store post references rather than copies, so a change in one screen shows everywhere.
- **Reads:** views read through repositories, which load from `LocalStore` first. A cold start renders the last saved feed with no network wait. Then each repository refreshes from the network (stale-while-revalidate).
- **Outbox** (`Persistence/Outbox.swift`): every write goes through it. That covers posts, comments, reactions, saves, join and withdraw, approve and decline, messages, chat read receipts, notification reads, preferences, `/me` patches, reports, blocks and device registration.
  - One row per `clientId`, sent unchanged on every retry, so the server dedupes.
  - Toggles such as reactions and preferences **coalesce** into one pending write.
  - Transient failures (offline, 5xx, 429) retry with exponential backoff: base 2 s, ×2, ±20 % jitter, cap 15 min, 10 attempts, and `Retry-After` is honoured. Client errors fail fast and roll back the optimistic change.
  - It drains on `NWPathMonitor` reconnect, on foreground, after each enqueue, at the next retry time, and from a `BGProcessingTask` (`in.unsolo.app.outbox`).
- **Sync:** `GET /sync?since=` runs on launch, on foreground and from a `BGAppRefreshTask` (`in.unsolo.app.refresh`). It refetches changed posts, drops removed ones, and updates memberships and the unread count.
- **Offline banner:** "Offline · showing saved" (plus "N waiting to send") appears when the path is down or requests fail as offline.

### Optimistic publishing and uploads

`TribeRepo.publish` and `Repositories/UploadCoordinator.swift`:
1. The post is written to the store at once as a local `sending` post and shown at the top of the feed, using the local photo.
2. A `POST /posts` is queued with the `clientId` and one upload slot per photo.
3. Off the main actor, each photo goes through `ImageCompressor`: ImageIO downsample to a long edge ≤ 2048, re-encode as JPEG (HEIC input works), and step quality and size down until it is ≤ 2,097,152 bytes. The JPEG is written from a fresh `CGImage`, so all EXIF data, including GPS, is stripped. Tests check this.
4. Each JPEG is uploaded as multipart `POST /uploads` (`file`, `purpose`) on a **background `URLSession`** (`in.unsolo.app.uploads`, launch events on). The card shows progress.
5. When every slot has its `Media`, the outbox sends `POST /posts` with the media injected. The server copy replaces the local one.
6. If `moderation.state == "held"`, the "Charging for this?" sheet offers three choices: edit (PATCH and re-screen), "It's not commercial", or "List it as a hosted trip".
7. Unresolved uploads resume on the next launch.

Demo mode swaps in `DemoUploader`, which simulates progress and keeps the local file as the media URL. The `publishPlan` start screen runs this whole path.

### Images

`PcAsyncImage` + `ImagePipeline` (an actor):
- **Caches:** an NSCache of decoded bitmaps (keyed by URL and pixel bucket), plus a disk cache of original bytes in `Caches/images`. The disk cache is LRU by file modification date and trimmed to stay under about 150 MB.
- **Progressive:** shows `lqip` (a base64 `data:` URI) or `thumbUrl` first, then crossfades to `url`.
- **Data saver** (Settings) loads `thumbUrl` only.
- Every image is downsampled with `CGImageSourceCreateThumbnailAtIndex` to the rendered size times the screen scale.

### Push notifications

`Services/PushManager.swift`:
- **Permission** is requested after the first post or join request, never at launch. Debug Settings also has "Send a test notification".
- **Registration:** `registerForRemoteNotifications`, then the hex token goes to `POST /devices` (`platform: "ios"`) through the outbox. Sign-out calls `DELETE /devices`.
- **Categories:** `plans`, `replies`, `messages` (inline Reply) and `trips`, plus `join_request` with Approve and Decline actions.
- **Presentation and routing:** banners show in the foreground. Tapping one routes `link` through the validated deep-link parser and logs `push.open`.
- **On the simulator:** `registerForRemoteNotifications` fails because there is no `aps-environment` without signing. The failure is logged and the app carries on.
- **Sample payloads:** `mobile/ios/push-samples/*.apns`, for `join-request`, `reply`, `message` and `trip-reminder`:

  ```sh
  xcrun simctl push booted in.unsolo.app mobile/ios/push-samples/join-request.apns
  ```

  Allow notifications first by posting or joining once, or with Settings → Send a test notification.

### Notification links and inline join decisions

- **Same-site check:** a notification or push `link` is routed only if it is a same-site path. It must start with `/`, must not start with `//` or `/\`, and must contain no whitespace or control characters (`DeepLink.isSameSitePath`). Anything else, or a safe but unknown path, opens Activity.
- **Inline Approve/Decline:** `Notification.postId` and `actorId` (optional Tribe fields) drive Approve/Decline on `tribe_join_request` rows in Activity and on the push actions. The call is `POST /posts/{postId}/requests/{actorId} { decision }`, which goes through the outbox. Push payloads read `postId` + `actorId`, falling back to the legacy `userId` key.
- **Offer accept:** `POST /offers/{id}/accept` sends `{ expectedPricePaise }` (the price the organiser was shown). On 409 the review screen shows "The host changed this offer. Review the new price." and refetches the offer. `DemoTransport` enforces the same rule: 400 without the field, 409 on a mismatch. `DemoBackend.setOfferPrice` simulates a host edit.

### Deep links

`Services/DeepLink.swift` handles universal links (`https://unsolo.in` and `www.unsolo.in`) and `unsolo://`, through `.onOpenURL` and `NSUserActivityTypeBrowsingWeb`.

Supported paths: `/tribe`, `/tribe/p/{uuid}`, `/p/{uuid}` (share links), `/packages/{slug}`, `/profile/{username}`, `/chat/{uuid}` and `/bookings`.

Validation:
- Ids must be UUIDs.
- Slugs must match `^[a-z0-9]+(-[a-z0-9]+)*$`.
- Usernames must match `^[A-Za-z0-9_.]{2,32}$`.
- Other hosts, plain http, extra segments and anything else are ignored.

Associated Domains (`applinks:unsolo.in`, `applinks:www.unsolo.in`) and `aps-environment` are in `UnSOLO/UnSOLO.entitlements`. That file is referenced by the build but has no effect until the build is signed.

### Location, analytics and the landing prompt

- **Location** (`Services/LocationService.swift`):
  - When-In-Use only, with `desiredAccuracy = kCLLocationAccuracyReduced`.
  - Permission is asked only when the user turns on Settings → "Suggest things near me".
  - Coordinates are rounded to 2 decimals (about 1 km) before they reach `/feed` or `/suggestions`.
- **Analytics** (`Services/Analytics.swift`):
  - The queue is persisted to disk and flushed every 30 s, on background, and in batches of up to 50 to `POST /events`.
  - Each event carries `anonId` (stable per install) and `sessionId` (new after 30 min in the background).
  - Names are validated against `^[a-z][a-z0-9_.]{1,63}$` and props are capped at 4 KB.
  - Events sent: `app.open`, `screen.view`, `trip.view`, `trip.take_seat`, `post.create`, `post.react`, `post.comment`, `plan.join_request`, `plan.approve`, `share.plan`, `push.open`, `landing.prompt_shown`, `landing.prompt_accepted` and `suggestion.tap`.
- **Landing tab:**
  - Tab opens are counted locally and also sent as `screen.view`.
  - The initial tab is the saved landing tab from `UserDefaults`, with no network wait.
  - On launch, a signed-in user gets `GET /me/landing-suggestion`. If it suggests a tab, a small sheet asks "You open Tribe most. Start the app on Tribe?". Accepting sends `PUT /me/preferences`; declining sends `POST …/dismiss`.
  - Guests use the same rule evaluated locally: the most-opened tab over 14 days, at least 3 opens, not the current tab, not dismissed.

### Security and privacy

- Tokens are stored only in the Keychain.
- No secrets are in code. The anon key comes from `/config`.
- ATS is on, with the localhost-only exception.
- Deep-link parameters are validated.
- Phone numbers are masked in Settings.
- The privacy manifest (`UnSOLO/Resources/PrivacyInfo.xcprivacy`) declares:
  - UserDefaults (`CA92.1`) and file timestamp (`C617.1`, used by the image cache LRU).
  - Collected data: name, email, phone, coarse location, photos, user content, product interaction and device ID.
  - No tracking.

## Contract gaps

These are things the app needed that `api-v1.md` doesn't define. For each one, the app either works around the gap or disables the feature. Nothing invents new server behaviour, except where a workaround is noted.

1. **Push payload for actions.** iOS action buttons need `aps.category` (for example `tribe_join_request`), but the contract only specifies `aps.thread-id`. The APNs row should also list the `type`, `postId` and `actorId` custom keys. The app reads them, and `push-samples/join-request.apns` carries them.
2. *(Resolved.)* Notification rows now carry `postId` and `actorId`. Older `join_request` rows without them still fall back to `/posts/{id}/requests`.
3. **"It's not commercial" for held posts.** The spec says a held post goes live once it is edited or confirmed as non-commercial, but no field is defined for confirming. The app sends `PATCH /posts/{id} { confirmNonCommercial: true }`, which the demo honours. This needs a server decision.
4. **Poll votes.** There is no vote endpoint, so the app votes with `POST /posts/{id}/comments { pollChoice, body: "Voted: <label>" }`. A `PUT /posts/{id}/poll { optionId }` would avoid the filler comment.
5. **"Plans looking for a host".** There is no endpoint for the host demand board. The app uses `/feed?kind=plan` and filters out the host's own plans. Also missing: which offers this host has already made, and the host hub's earnings, payouts and "This week" departures.
6. **Follow / unfollow.** The profile returns `isFollowing` and counts, but there is no endpoint. The Follow button is disabled.
7. **Plan chat room.** `Post` has no `chatRoomId` for the organiser and approved members, and `/chats?type=` has no `plan` type. The demo uses `general`. "Plan chat" opens Messages.
8. **Trip fields used by the mockups but missing:**
   - route or summary line, pace/difficulty, and category on `TripLite`
   - itinerary ("Day by day") on `TripDetail`
   - seat number, pickup point and balance due date on `Booking`
   - aggregate demographics ("4 women · 3 men")
9. **Explore Tribe bridge** ("14 people are planning Himachal · 3 plans in December · 6 new stories"). This isn't in `/explore`. The app uses the lead trip's `planningCount` plus `stories.count`.
10. **Status stories (24 h strip) and "Going your way".** Both appear in the Tribe mockups, but there is no endpoint for either. Not built.
11. **Story tagging consent.** There is no endpoint to list co-travellers of a past booking or to answer a tag (`post_tags`). The composer offers the trip's `goingFaces` and sends `tagUserIds`.
12. **Saved posts.** `PUT/DELETE /posts/{id}/save` exist, but there is no list endpoint (`GET /me/saved`).
13. **Audience.** The mockup has "People I follow", but `audience` only allows anyone/women/verified. The "I approve each request" toggle has no field either (the app treats it as always on).
14. **`/sync.notifications` type.** Not specified. The app treats it as a count, the same as `unreadNotifications`.
15. **`DELETE /devices` with a JSON body.** Some proxies drop DELETE bodies. Consider `DELETE /devices/{token}`.
16. **Web checkout session handover.** "The session is handed over with a deep link" isn't specified (no token-exchange endpoint or URL format). Until it is, users may need to sign in again on the web inside `SFSafariViewController`.
17. **Image messages in chat.** `type: "image"` exists, but there is no way to send one. Text only.
18. **Upload `purpose` for plan and ask photos.** The app uses `post`, and `story` for stories.
19. **`tripPackageId`.** The app assumes `TripLite.id` is the package id.

## Limitations and known gaps

These are honest notes on what is stubbed, untested or missing.

- **No live backend testing.** Every flow was exercised against `DemoTransport` and unit tests. Live mode (`-demoMode NO` or Release) compiles and is wired to the contract but has never talked to a real server.
- **Push:**
  - APNs registration can't succeed without a developer ID. On the simulator it fails gracefully and is logged.
  - Actions and routing are implemented and `simctl push` delivers the samples, but tapping Approve from a real push has not been verified end to end.
- **Background tasks and uploads:**
  - The background upload session runs only through `DemoUploader` in demo mode. The real multipart upload to `/uploads` is untested.
  - BGTask handlers are registered but were not force-triggered. To test one, pause in the debugger and run:

    ```
    e -l objc -- (void)[[BGTaskScheduler sharedScheduler] _simulateLaunchForTaskWithIdentifier:@"in.unsolo.app.refresh"]
    ```

- **Payments** stay on the web (`SFSafariViewController`), as the contract says. There is no native seat-hold or ticket stamp animation.
- **Sign in with Apple** is shown disabled.
- **Not built:**
  - share-card image rendering (the system share sheet gets text + link)
  - leaderboard
  - saved-posts list
  - full edit-profile form (gender is editable in Settings)
  - status stories strip
  - Explore load-more (Tribe feed pagination is wired)
  - month filter UI
  - search filters beyond text
- **Layout:** iPhone only, portrait. iPad and desktop layouts are not done.
- **Fonts:** the system font is used instead of IBM Plex, as instructed (no font downloads).
- **Accessibility:** VoiceOver labels, traits and Dynamic Type are in place, but nothing has been audited with Accessibility Inspector or at the largest text sizes.
- **Landing prompt in demo:** the fixture always suggests Tribe, so the prompt appears on normal Debug launches until it is accepted or dismissed. That is intended, to show the feature.
- **Mockup differences:**
  - In dark mode the "UN" tile disappears against the dark ground, which follows direction.md (gold UN + light SOLO on dark).
  - In iOS 26 the system navigation bar buttons use Liquid Glass, so the back and share buttons look slightly different from the flat mockups.
